One Minute: Building a Narration-Free Knowledge Video with Code

Created2026-11-15|Updated2026-11-15|Personal Website
|Word Count:4.5k|Reading Time:27mins|Post Views:

The 61-second film on this site (/video) wasn’t cut in an editor and wasn’t a template with the text swapped out. It was written — React components for the picture, numpy for the score, npm run render for the mp4. I never opened Premiere, After Effects, or CapCut once.

This post lays the whole process out: what to install, how to lay out the timeline, how each of the twelve scenes is drawn, how the music is synthesized, and how it all gets rendered. The code is real and it runs.

Let’s be clear about what this path is for. It suits information-dense, text-forward, graphics-supported knowledge videos: explainers, retrospectives, promos, course clips. It does not suit anything needing a human on camera, live footage, or elaborate transition effects. Its strength is that it is version-controllable — change one number, re-render, the whole film follows. Its weakness is that every shot is yours to write, with no stock library to fall back on.

Twelve scenes, one tsx file each. I stitched this contact sheet with ffmpeg to check one thing: does every screen actually have something on it?

1. Why not use an editor

Motivation first, or this whole approach looks like self-inflicted pain.

A one-minute film in an editor takes three or four hours: record against the script, hit the beats, hunt for footage, grade, sync. Then do it again for the next cut. By version five you no longer remember why version three made the choices it did.

Doing it in code is slow the first time — environment, components. But from the second film onward the cost falls off a cliff:

  • Script changed? Edit one line in script.json, re-flow the timeline, re-render. Three minutes.
  • A screen feels empty? Open that one tsx, add a chart, render that single frame (remotion still) — no full render.
  • Want a different palette? Change eight hex values in theme.ts, the whole film follows.
  • Want a vertical cut? Change two numbers.

And it’s inherently traceable — every change lives in git, with screenshots.

This way of working has a name now: vibe coding. You tell the AI “the third screen is too empty, add a real publish timeline with axes”, it edits the code, you watch the result in the browser. You own taste and judgement; it does the typing. This film’s 3,600 lines of tsx came out of exactly that loop.

2. What to install

Three things, all free.

Step one: Node.js

node -v   # anything above v20 works; I'm on v23

Step two: ffmpeg

Remotion uses it to encode. On Windows grab the essentials build from gyan.dev, extract it, and put its bin folder on PATH.

ffmpeg -version   # a version number means you're done

Step three: a Chromium-based browser

Remotion works by screenshotting a browser, frame by frame, so it needs a Chromium. It will try to download chrome-headless-shell itself — and in China that download frequently stalls (it cost me half an hour). If you already have Chrome or Edge, just point Remotion at it:

// remotion.config.ts
import { Config } from "@remotion/cli/config";

Config.setVideoImageFormat("jpeg");
Config.setOverwriteOutput(true);
Config.setConcurrency(4);

// No Chrome on this machine — use the system Edge (Chromium) as the render engine.
Config.setBrowserExecutable(
  "C:\\Program Files (x86)\\Microsoft\\Edge\\Application\\msedge.exe",
);

⚠️ Gotcha: this one line is the biggest time-saver for Windows users. Without it Remotion fetches a few hundred megabytes of headless shell from Google, which basically doesn’t complete from mainland China. Windows 10/11 always ships Edge at exactly that path — copy it.

Step four (optional): three Python packages

The score is synthesized in Python and needs numpy and scipy:

pip install numpy scipy

3. Create the project

npm create video@latest blog-promo
cd blog-promo
npm i

Four dependencies, all official Remotion:

{
  "dependencies": {
    "@remotion/cli": "^4.0.539",
    "react": "^19.3.0",
    "react-dom": "^19.3.0",
    "remotion": "^4.0.539"
  },
  "devDependencies": {
    "typescript": "^7.0.2"
  }
}

The layout ends up roughly like this:

script.json              per-scene minimum duration and gap
tools/build-timing.mjs   lays out the timeline → src/timing.json
tools/make-score.py      synthesizes the score → public/score.wav
tools/check-score.py     checks the score: loudness / bands / pulse / stereo width
tools/shots.mjs          batch still frames (use this instead of full renders)
src/timing.json          [generated] from/to per scene
src/theme.ts             palette, fonts, easing, stable pseudo-random
src/components/          per-character reveal, hairlines, mono labels, grain, HUD
src/film/BlogPromo.tsx   the reel: exit→enter, audio mount, HUD progress
src/film/scenes/*.tsx    twelve scenes, one file each
public/score.mp3         the score (final)

The key design decision: timeline and picture are separate. script.json only declares “what this scene says, the minimum seconds, how much white space after”. A scene never knows which second it starts at — it receives frame, start, end and computes its own local progress. Reorder scenes or change durations and not one line of scene code changes.

4. Write the words first: script.json

Twelve scenes. Write the copy before any code.

[
  {
    "id": "01-open",
    "sub": "there is nothing here",
    "note": "empty screen, a point of light",
    "min": 3.2,
    "gap": 0.35
  },
  {
    "id": "02-who",
    "sub": "a Data person\nwho doesn't really do tech\nwrote twenty-four things here",
    "note": "who I am",
    "min": 4.4,
    "gap": 0.3
  },
  {
    "id": "03-fragments",
    "sub": "OceanBase's log stream\nSeata's state machine\na servo that costs forty cents",
    "note": "fragments",
    "min": 5.4,
    "gap": 0.3
  }
]

Four fields: id maps to a file name, sub is the meaning of the scene (not subtitle text), min is the shortest acceptable dwell in seconds, gap is the white space after it.

The structure of the whole film: nothing → who I am → what I write about → these things look unrelated → but I used to think otherwise → so I wrote it down → how much there is → there’s a deep gap in between → the crossing is all recorded here → this isn’t a tutorial → signature → address. The last five scenes are one emotional landing; the first seven are setup.

5. The timeline: everything on 60 BPM

This is the single most important technical decision in the film.

The score is 60 BPM — one beat is exactly one second. So if every scene’s duration rounds up to whole seconds, and every gap rounds to whole seconds too, then every cut lands on a beat and picture and music stay locked forever. No manual nudging.

// tools/build-timing.mjs
const FPS = 30;
const BEAT = 1.0; // seconds
const BAR = BEAT * 4;

const scenes = [];
let t = 0;
for (const s of script) {
  const raw = s.min ?? 4;
  const beats = Math.max(1, Math.ceil(raw / BEAT));  // round up to a whole beat
  const dur = beats * BEAT;
  scenes.push({ id: s.id, startSec: round(t), endSec: round(t + dur), beats });
  // Critical: gaps must also land on beats, or the cuts drift one beat at a time
  const gapBeats = Math.round((s.gap ?? 0) / BEAT);
  t += dur + gapBeats * BEAT;
}

// Head and tail padding: one second of black up front, 2.4 seconds of tail
const LEAD = 1.0;
const TAIL = 2.4;

⚠️ Gotcha: gaps must be beat-aligned. My first version rounded only the scene durations and left gaps at values like 0.35s. Every scene then drifted an extra 0.35s — by scene eight the picture had cut but the kick hadn’t arrived, half a beat late, and it looked wrong in a way you can’t quite name. Every time value must be an integer multiple of one second.

The output is a timing.json that looks like this:

{
  "fps": 30,
  "width": 1920,
  "height": 1080,
  "bpm": 60,
  "totalSeconds": 61.4,
  "totalFrames": 1842,
  "scenes": [
    { "id": "01-open", "startSec": 1, "endSec": 5, "from": 30, "to": 150 },
    { "id": "02-who",  "startSec": 5, "endSec": 10, "from": 150, "to": 300 }
  ]
}

from / to are frame numbers, consumed directly by the scenes.

Each scene rounds up to whole seconds; so does each gap. 61.4 seconds = 1842 frames. The beads along the bottom are the beats.

6. The reel: exit first, then enter

This is the easiest thing to get wrong, so it gets its own section.

My first version used a cross-dissolve — the outgoing scene fades out while the incoming one fades in. Sounds natural, right? It was a disaster: every screen in this film is big centred type, so during the dissolve “Data person” and “OceanBase” overlapped into a black smear.

So: exit first, then enter. The old scene is fully gone 7 frames before the cut, the new one starts 7 frames after it, and between them sits a 1-frame near-black slit (1/30 s). The eye reads it as a hard cut, and nothing ever smears.

// src/film/BlogPromo.tsx
scenes.map((s, i) => {
  const next = scenes[i + 1];
  const cut = next ? next.from : timing.totalFrames;

  const OUT = 7;   // exit over 7 frames
  const IN = 7;    // enter over 7 frames

  if (frame < s.from || frame >= cut + IN) return null;

  const enter = interpolate(frame, [s.from, s.from + IN], [0, 1], CLAMP);
  const out = next
    ? interpolate(frame, [cut - OUT, cut], [0, 1], CLAMP)
    : 0;

  const opacity = enter * (1 - out);
  if (opacity <= 0.001) return null;

  // Enter 0.988 → 1, exit 1 → 1.028 — same direction, like a camera always pushing in
  const scale = 0.988 + 0.012 * enter + 0.028 * out;
  const blur = out * 12 + (1 - enter) * 7;

  return (
    <AbsoluteFill style={{ opacity, transform: `scale(${scale})`,
                           filter: blur > 0.05 ? `blur(${blur}px)` : undefined }}>
      <Body frame={frame} start={s.from} end={s.to} />
    </AbsoluteFill>
  );
})

Two details worth stealing:

  1. scale moves monotonically. Entering goes 0.988 → 1, exiting goes 1 → 1.028. The camera is always pushing slowly forward; an exit is “passing through”, not “pulling back”.
  2. Exits blur. blur = out * 12 — up to 12px at the end of an exit. Big centred type shrinking and softening reads as “leaving focus”, which is far more elegant than a plain fade.

The two opacity curves never overlap. That one-frame slit at the cut is why nothing smears.

7. How one screen gets drawn

By now the environment works, the timeline exists, the reel is solved. What’s left is the time-consuming part: twelve screens, one at a time.

Start with one hard rule, earned the hard way:

Big type is a conclusion. A chart is what makes anyone believe it.

My first version had one line of big type on black per screen. It looked classy to me. The verdict from outside was “too empty, there’s nothing there”. Compared against the reference film the gap was obvious: every one of its screens has something you can look at frame by frame — axes with tick marks, an animating state machine, hundreds of simulated particles, data points you can count.

Example one: a five-replica log stream

Scene three, “fragments”, needs to convey “three scales”, the first being millisecond-level distributed consensus. Rather than write “distributed transactions are fast”, draw an actual majority commit:

// src/film/scenes/Fragments.tsx
const N = 5;          // five replicas
const LEADER = 2;     // the middle one leads
const CYCLE = 78;     // 78 frames per cycle

const l = Math.max(0, local);          // negative frames index below zero and crash
const step = Math.floor(l / 12) % 6;   // six phases, looping

// Replica disk height: the further from the leader, the lower
const diskAt = (i: number) => 8 + Math.abs(i - LEADER) * 11;

Then light up four Redo log entries phase by phase, count how many are lit into ack n/5, and only show COMMIT ✓ once three or more agree. What the viewer sees isn’t the word “majority” — it’s three bars lighting up and then a check appearing.

The other two columns of that scene draw a Saga state machine with a red dashed compensating edge (M 50% 16% Q 50% 72%, 12% 42%), and an SG90 servo’s real angle and PWM pulse width:

const ang = 90 + 80 * Math.sin((l / 72) * Math.PI * 2 - Math.PI / 2);
const pulse = 500 + (ang / 180) * 2000;   // 0.5ms – 2.5ms

The arm actually swings and the readouts beside it are {Math.round(ang)}° and {Math.round(pulse)} µs. Those numbers are correct — an SG90 really is 50Hz at 500–2500µs.

Example two: a real publish timeline

Scene seven, “how much”, has to say “I wrote 24 posts”. A giant 24 means nothing. So I turned the actual publish dates of all 24 posts into a scatter plot:

// src/film/scenes/Stats.tsx
const POSTS = [
  { d: [2024.17, 2024.18], w: 0.55, t: "Hexo + Github personal site" },
  { d: [2024.19, 2024.20], w: 0.48, t: "Simple NLP sentiment analysis" },
  // ...
  { d: [2026.83, 2026.84], w: 0.88, t: "OceanBase notes 3: HA and elasticity" },
];

const X0 = 2024.0;
const X1 = 2026.95;
const norm = (y: number) => (y - X0) / (X1 - X0);

Each dot is one post: x is the publish date, height is the length. And then the chart surfaces three things I hadn’t consciously registered:

  • There’s a huge dead zone — from mid-2025 into early 2026, nearly a year with nothing. The chart labels it “gap · 301 days”.
  • Five posts in the last seven days — those final four dots crowd together like a vertical line.
  • The cumulative curve goes flat across the dead zone.

This is exactly where a chart beats a number — there is no sentence that conveys a flattened curve.

💡 Lesson: for every screen, ask “what can the viewer count here, what trend can they see?” If the answer is “nothing”, that screen is empty, and more words won’t fix it. More drawing will.

8. Palette and type

The whole visual system is eight colours, applied globally:

// src/theme.ts
export const C = {
  bg: "#000000",     // pure black
  bg2: "#08090A",    // secondary black
  ink: "#F2F2F0",    // off-white (pure white is harsh on pure black)
  inkDim: "#9BA09C", // secondary text
  mute: "#5E635F",   // footnotes, hairlines
  lime: "#D8FD58",   // the only accent
  limeDim: "#8FA83A",// the accent's dimmer sibling
  red: "#F1574D",    // reserved for "wrong" and "missing"
} as const;

Three rules:

  1. One accent only. Fluorescent lime. Everything that needs to be seen is lime; everything else is greyscale. Add colours and the accent stops meaning anything.
  2. Red only means negative. Red appears three times in the film: three “0 points” on one screen, one “no textbook”, and “the next post is always being written”.
  3. Serif for headlines, sans for body, mono for data. Keep the division strict; mixing reads as carelessness.
export const F = {
  serif: '"Noto Serif SC", "Songti SC", "SimSun", serif',
  sans:  '"Microsoft YaHei UI", "Microsoft YaHei", "Noto Sans SC", sans-serif',
  mono:  '"Cascadia Mono", "Consolas", ui-monospace, monospace',
};

The background isn’t flat black either — there’s an SVG grain layer (feTurbulence, opacity 0.055) and a radial vignette on top. Pure black reads as “dead” on most displays; a touch of noise gives it texture instantly, and it costs almost nothing in bitrate.

// src/components/Backdrop.tsx
<svg>
  <filter id="grain">
    <feTurbulence baseFrequency="0.82" numOctaves="3" />
  </filter>
  <rect width="100%" height="100%" filter="url(#grain)"
        opacity={0.055} style={{ mixBlendMode: "overlay" }} />
</svg>

9. Motion: three functions are enough

Across 3,600 lines, all the motion comes from three functions.

// Map a frame number to progress in 0→1, clamped outside the range
export const prog = (frame: number, start: number, dur: number) =>
  Math.min(1, Math.max(0, (frame - start) / dur));

// 0→1, fast then slow. Every "explode" entrance uses it
export const easeOutExpo = (t: number) => (t >= 1 ? 1 : 1 - Math.pow(2, -10 * t));

// Stable pseudo-random. Remotion renders concurrently across threads, so
// Math.random() resolves differently on different workers and the picture flickers.
// Use a deterministic hash instead.
export const rnd = (n: number): number => {
  const x = Math.sin(n * 127.1 + 311.7) * 43758.5453;
  return x - Math.floor(x);
};

⚠️ Gotcha: never use Math.random() for particles, star fields, or jitter. Remotion splits 1,842 frames across 8 processes. Each process seeds Math.random() differently, so the same star lands somewhere completely different on frame 100 and frame 101 — the finished film sparkles with noise. Use a hash keyed on the index, like rnd(i), so index i always yields the same number.

Usage is direct. The opening’s 140 motes of dust, for instance, are generated once in useMemo:

const stars = React.useMemo(
  () => Array.from({ length: 140 }, (_, i) => ({
    a: rnd(i * 3.1) * Math.PI * 2,          // angle
    d: 0.25 + rnd(i * 7.7) * 0.75,          // distance factor
    delay: rnd(i * 5.5) * 34,               // delay in frames
    drift: 0.85 + rnd(i * 13.9) * 0.5,      // drift speed
  })),
  [],
);

Then the per-character reveal — every character rises and deblurs:

const p = easeOutExpo(prog(frame, start + i * stagger, 16));
<span style={{
  opacity: p,
  transform: `translateY(${(1 - p) * 0.22}em)`,
  filter: p < 0.995 ? `blur(${(1 - p) * 12}px)` : undefined,
}}>{ch}</span>

stagger defaults to 1.4 frames — each character appears 1.4 frames after the previous. That’s 21 characters a second: it reads like someone typing, without the mechanical feel of a typewriter effect.

10. The score: eight layers of numpy

This is the most “unreasonable” part of the whole thing. There is no narration, so the music is the only emotional thread — it can’t be some track you found, it has to follow the picture.

So I measured the reference. I pulled the audio from Emergence · An Epic of Parameters on Bilibili and ran spectral analysis:

Metric Reference, measured
Tempo 60 BPM (autocorrelation peak 0.636)
20–120Hz share 57.6%
120–400Hz 21.3%
400Hz–2kHz 13.6%
2k–8kHz 7.5%
Low-end hit spacing 0.75–1.75s (sparse, not four-on-the-floor)

The conclusion is unambiguous: more than half the energy is sub-bass, very little mid/high, and the hits are sparse. This isn’t pop music; it’s ambient.

So: no samples, no network, pure synthesis. Eight layers:

Layer Role Sound
PAD chord bed, the film’s body Dm–Bb–F–C loop, 8s per chord
SUB sub-bass drone root an octave down, mono
ARP mid-range arpeggio, the actual melody chord tones +2 octaves, one per beat
SHIMMER high overtone layer thirds/fifths +2 octaves, slow vibrato
BELL high sparkle one every 2 beats, alternating sides
PULSE sparse low hit pitch-dropping “heartbeat” every 2 beats
NOISE air bed + transition riser band-swept noise for 1.6s before each cut
IMPACT section downbeat a hit on 5 key scenes

The mechanism that matters is the LAYERS instrumentation table — one row per scene, controlling each layer’s gain in that section:

# tools/make-score.py
LAYERS = {
    "01-open":  dict(pad=0.35, sub=0.55, arp=0.00, shim=0.00, pulse=0.10),
    "04-why":   dict(pad=0.70, sub=0.80, arp=0.10, shim=0.15, pulse=0.00),
    "05-turn":  dict(pad=1.00, sub=1.00, arp=0.45, shim=0.22, pulse=0.04),
    # ...
}

So on “these things look unrelated” the pulse drops out and the noise rises — picture and music go quiet together. On “I used to think it was like that” every layer is at full. Within a section the first 55% holds and the last 45% crossfades, so change only happens near cuts, never as a mid-section jump.

After synthesis there’s a processing chain whose order matters:

x = np.tanh(x * 1.30) / 1.30        # soft saturation, tame the peaks
x = highpass(x, 2600, gain=0.85)    # lift the highs
x = highpass(x, 55) - lowpass(x, 130) * 0.22   # tighten the low end
x = fade_in(x, 2.2) * fade_out(x, 3.4)        # head and tail fades
x = x / np.abs(x).max() * 0.891     # peak-normalize

Then one pass of loudness normalization through ffmpeg — this step is mandatory:

ffmpeg -y -i public/score.wav \
  -af "loudnorm=I=-12:TP=-0.8:LRA=9" \
  -c:a libmp3lame -b:a 256k public/score.mp3

I=-12 is the target loudness, TP=-0.8 the peak ceiling. It measured -11.7 LUFS / true peak -0.6 dBTP, which matches mainstream streaming targets — nobody has to max out their volume to hear it, and nothing clips.

⚠️ Gotcha: don’t write your own compressor. I tried a first-order IIR envelope follower for dynamics, about two hundred lines, and RMS actually got worse — from -14 to -17.5dB. The envelope estimate was wrong and the gain kept pumping. Hand it to ffmpeg’s loudnorm; one line beats two hundred.

Left: the four band shares side by side (reference vs mine). Right: long-term average spectrum. Mine leans harder on the low-mids — the reference has narration filling that region, whereas a narration-free film must have content between 400Hz and 2kHz or it sounds like a hum rather than a piece of music.

11. Never re-render the whole film

This one step saves you 80% of your waiting.

A full render is 1,842 frames at 1080p30 and takes three minutes. If you’re waiting three minutes per tweak, a day of that will break you. So write a still-frame script:

// tools/shots.mjs
for (const f of frames) {
  const out = path.join(OUT, `f${String(f).padStart(5, "0")}.jpg`);
  if (!fs.existsSync(out)) {                    // skip if it's already there
    execFileSync("npx", [
      "remotion", "still", "BlogPromo", out,
      `--frame=${f}`, "--image-format=jpeg", "--jpeg-quality=92",
    ], { cwd: ROOT, stdio: "inherit", shell: true });
  }
}

node tools/shots.mjs --scene grabs the midpoint of every scene — twelve images in about twenty seconds. Change one screen, look at it, done.

⚠️ Gotcha: that existsSync skip will bite you. If you forget to delete old frames after changing a scene, the script hands you the previous screenshot and you’ll sit there hunting a bug in the old picture. Remove-Item out/check/*.jpg after every change.

12. Shipping

# Master: high quality
npx remotion render BlogPromo out/BlogPromo.mp4 --concurrency=8

# Web: CRF 26, for embedding in the blog
npx remotion render BlogPromo out/BlogPromo-web.mp4 --crf=26 --concurrency=8

Same film, two bitrates:

Master Web
Size 5.7 MB 4.1 MB
Setting default CRF 18 --crf=26
Use archive, uploads embedded on-site

--concurrency=8 means eight parallel processes. Scale it to your cores — my machine (Ultra 9 + 5080) is sweet at 8 and gets slower at 16 because of context switching.

13. Every mistake, in one place

1. A cross-dissolve smears big centred type. Already covered. Worth seven frames.

2. Math.random() makes the whole film strobe. Use a deterministic hash under concurrent rendering.

3. Negative frames index below zero and crash. A scene’s frame - start is negative on some boundary frames, Math.floor(local / 22) becomes -1, and then arr[-1].x throws Cannot read properties of undefined. One line — Math.max(0, local) — fixes it.

4. Beat-misaligned gaps drift the whole film. Every time value must be a multiple of one second.

5. Never put absolutely positioned divs inside <svg>. I dropped three <div>s into an SVG and they rendered as nothing at all, with no error — I spent ages on still frames assuming the animation wasn’t firing. SVG may only contain SVG elements.

6. Chinese text can be tofu boxes in PIL. consola.ttf renders CJK as a row of squares. Switch typefaces by checking for CJK characters:

_cjk = re.compile(r"[\u3000-\u9fff\uff00-\uffef]")
path = F_MONO if not _cjk.search(s) else (F_SERIF if serif else F_SANS)

7. Windows Smart App Control blocks ffmpeg. This machine has SAC on, and the unsigned ffmpeg.exe inside node_modules gets Permission denied writing to the system TEMP. Point TEMP at the project instead:

$env:TEMP="D:\DeepSeekWorkspace\.tmp"; $env:TMP=$env:TEMP

8. Don’t count on mermaid. It’s disabled in this blog’s theme. Every figure in this post is a PNG, drawn with PIL or grabbed with ffmpeg.

14. So where’s the “vibe”

It isn’t just “AI writes code for you”. The real change is in iteration speed.

In the traditional workflow, changing one screen costs “open the app, find that shot, edit, preview, export a segment”. Ten minutes, minimum.

On this path, changing one screen costs “edit one tsx, render one frame, look”. Twenty seconds.

Drop the cost by an order of magnitude and your standards shift. Where you used to think “this’ll do”, you now think “this screen is still empty, replace it”. Cheap retries are what let you try five things instead of settling for one.

The film went through four major revisions:

  • v1: twelve screens of big type plus narration. Verdict: “too empty”.
  • v2: narration removed, the score rebuilt in eight layers. Verdict: “why is there still narration” (the code hadn’t been fully deleted).
  • v3: eight screens redrawn with real charts. I thought it was done.
  • v4: the last three screens (Who / Stats / Gap) got more data — a cumulative curve, depth ticks, a 962-day evidence bar.

Every version was “render it → look → delete → rewrite”. Without that twenty-second feedback loop, I would have shipped v3.

15. Source code

The whole thing lives on one machine and isn’t open sourced (the content data is all personal). But the structure is section 3 — build it yourself and you can have a moving “Hello World” in two hours.

If you just want to watch:

  • The film: One Minute
  • The reference: Emergence · An Epic of Parameters, BV1vXHr6eEoN on Bilibili. This film’s visual language, pacing, and score strategy all come from it.
  • Remotion docs: remotion.dev. Genuinely well written, and I mean that.

One last honest note: this path isn’t for everyone. If you make one video a year, the setup cost won’t pay back. But if you’re the sort of person who wants a video for every post, or you do courses, product explainers, or year-end reviews — write it once, and every film after that is just changing parameters.

My next one will almost certainly be built the same way.
